# 태그 기능 PRD

> 노트 태그 기능의 제품 요구사항 정의서(PRD). 구현 세부 명세는
> [`spec-fixed.md`](./spec-fixed.md)를 단일 기준(source of truth)으로 삼고,
> 이 문서는 **무엇을·왜** 만드는지와 의사결정 기록을 다룬다.

## 1. 개요

노트에 태그를 추가·삭제하고, 노트 상세(편집) 화면에서 태그 목록을 확인할 수 있는 기능을
제공한다. 태그는 노트를 분류·식별하기 위한 짧은 문자열이며, `Note` 데이터 모델에
`tags: string[]` 필드로 저장된다.

- **대상**: 노트 앱 사용자.
- **배경**: `src/types/note.ts`의 `Note` 인터페이스에 `tags`가 의도적으로 비어 있어,
  강의 진행에 맞춰 태그 기능을 점진적으로 추가하도록 설계되어 있다.
- **목표**: 노트당 자유 입력 태그를 부여해 분류 기반을 마련한다 (검색·필터는 후속 범위).
- **성공 기준**: 편집 화면에서 태그를 추가/삭제할 수 있고, 새로고침 후에도 서버에
  반영된 태그가 유지된다.

## 2. 사용자 스토리

- **US-1 (태그 추가)**: 사용자로서, 노트에 태그를 추가하여 노트를 분류·식별하고 싶다.
  - 입력란에 텍스트를 입력하고 Enter 또는 쉼표(,)로 태그를 확정한다.
  - 확정된 태그는 칩(chip)으로 표시된다.
- **US-2 (태그 삭제)**: 사용자로서, 노트에 추가된 태그를 삭제하여 잘못 추가한 태그를
  정리하고 싶다.
  - 칩에 마우스를 올리면 나타나는 × 버튼으로 해당 태그를 삭제한다.
- **US-3 (태그 확인)**: 사용자로서, 노트 상세(편집) 화면에서 현재 태그 목록을 칩으로
  한눈에 확인하고 싶다.
- **US-4 (생성 시 태그 부여)**: 사용자로서, 새 노트를 작성하면서 태그를 함께 지정하고,
  최초 저장 시 본문과 태그가 같이 저장되길 원한다.
- **US-5 (편집 시 즉시 반영)**: 기존 노트를 편집할 때, 태그를 추가/삭제하면 별도의 저장
  버튼 없이 즉시 서버에 반영되길 원한다.

## 3. 기술 결정 (ADR)

> 구현 아키텍처는 **안 C(커스텀 훅 기반 합성)**로 확정했다. 데이터·UI·저장 시점은
> [`spec-fixed.md`](./spec-fixed.md)의 결정을 따르고, 아래 ADR은 그 결정의 근거와 결과를
> 기록한다.

### ADR-1: 태그 데이터 구조 — `Note`에 인라인 `string[]`

- **Context**: 백엔드 없이 `json-server`로 REST를 흉내 내는 학습 프로젝트이고, 모든 노트
  상태를 단일 `NotesContext`가 들고 있다. 태그를 어떤 형태로 모델링할지 결정해야 한다.
- **Decision**: `Note` 인터페이스에 `tags: string[]` 필드를 인라인으로 추가한다. 별도
  tags 컬렉션이나 `tagId` 참조 정규화는 쓰지 않는다. 기본값은 항상 `[]`, 기존 노트에
  `tags`가 없을 수 있으므로 읽는 쪽은 `note.tags ?? []`로 방어한다. 중복 판단은
  **정확 일치**(대소문자 구분), 저장도 입력 그대로.
- **Alternatives**:
  - 별도 `tags` 컬렉션 + `tagId[]` 참조(정규화): 전역 태그 관리·rename에 유리.
  - 태그-노트 N:M 매핑 테이블: 관계형 DB에 적합.
- **Consequences**: 단일 Context 구조에 가장 단순하게 맞고 PATCH 한 번으로 갱신 가능.
  대신 전역 태그 목록·일괄 rename은 비효율적이다(이번 범위 밖). 대소문자 정규화는 없다.

### ADR-2: 태그 입력 방식 — Enter/쉼표 확정 칩 + 순수 파싱 함수

- **Context**: 태그를 입력하는 UX를 정해야 하고, 입력 파싱에는 trim·쉼표 분리·빈값
  무시·중복 제거 같은 규칙이 얽혀 있다. 이 규칙을 어디에 둘지가 테스트 용이성을 좌우한다.
- **Decision**: 입력란 1개에서 **Enter 또는 쉼표(,)**로 태그를 확정하고 칩(badge)으로
  렌더한다. 삭제 ×는 칩 hover 시 노출하며 `aria-label`을 단다. 파싱·정규화 규칙
  (`trim`, `"a,b"` 분리, 빈 문자열 무시, 정확 일치 dedup)은 React에 의존하지 않는
  **순수 함수**(`src/lib/tags.ts`의 `parseTagInput`/`addTags` 등)로 분리한다 — 안 C의
  핵심 연결고리.
- **Alternatives**:
  - textarea 자유 입력 후 일괄 파싱: 칩 UX·즉시 피드백이 약하다.
  - 멀티셀렉트 드롭다운 / 자동완성 콤보박스: 전역 태그 목록이 필요해 범위를 초과한다.
- **Consequences**: 익숙한 칩 패턴을 제공하고, 엣지케이스를 순수 함수 단위 테스트로
  촘촘히 검증할 수 있다. 자동완성·기존 태그 제안은 후속 작업으로 남는다.

### ADR-3: 태그 저장 시점 — 편집 모드 즉시 저장 / 생성 모드 지연 저장

- **Context**: 기존 NoteEditor는 제목·내용을 '저장' 버튼으로 커밋한다. 태그도 같은
  버튼에 묶을지, 별도로 즉시 반영할지 결정해야 한다. 생성 모드는 아직 노트 `id`가 없어
  PATCH 대상이 없다는 제약이 있다.
- **Decision**: **편집 모드**(`selectedNoteId` 존재)에서는 칩 추가/삭제 **즉시**
  `updateNote(id, { tags })`로 서버에 반영한다. **생성 모드**(`isCreating`)에서는 칩을
  로컬 state에만 쌓아두고 최초 '저장'(`createNote`) 시 `tags`를 함께 전송한다.
  프로젝트의 "낙관적 업데이트 없음 — `await api.xxx()` 후 `setNotes`" 규약을 따른다.
- **Alternatives**:
  - 태그도 '저장' 버튼에 통합: 즉시성이 떨어지고 제목/내용 흐름과 결합된다.
  - 생성 모드에서도 즉시 저장(빈 draft 노트를 선생성): 미저장 노트가 서버에 남는다.
- **Consequences**: 편집 UX가 즉각적이고 생성 모드는 `id` 없는 상태를 자연스럽게
  처리한다. 대신 모드 분기 로직이 필요하며, 이 분기와 실패 처리(`console.error`)는
  ADR-4의 `useTags` 훅 안에 캡슐화해 컴포넌트에서 감춘다.

### ADR-4: 구현 아키텍처 — 커스텀 훅 기반 합성 (안 C)

- **Context**: ADR-2/3의 입력 파싱·모드 분기·즉시 저장 로직을 어디에 둘지 정해야 한다.
  세 가지 안을 검토했다 — A(NoteEditor 인라인), B(프레젠테이션 컴포넌트만 분리, 로직은
  NoteEditor 유지), C(순수 헬퍼 + 커스텀 훅 + 분리 컴포넌트).
- **Decision**: **안 C**를 채택한다.
  - 순수 헬퍼 `src/lib/tags.ts` — `parseTagInput`, `addTags` 등 React 비의존 함수.
  - 커스텀 훅 `useTags(selectedNoteId, isCreating)` → `{ tags, addTag, removeTag }`.
    모드 분기·즉시 저장·로컬 state를 캡슐화하고, 내부에서 `useNotes().updateNote`를
    호출한다.
  - 프레젠테이션 컴포넌트 `TagInput`/`TagList` — 콜백 주입, named export,
    `{ComponentName}Props` interface (기존 `NoteItem`의 콜백 패턴과 동일).
  - `NoteEditor`는 훅과 컴포넌트를 잇는 **얇은 조립**만 담당한다.
  - Context는 `createNote` 시그니처만 `(title, content, tags: string[])`로 확장한다.
    `api/notes.ts`의 함수는 `Omit`/`Partial` 타입 덕에 변경 불필요.
  - **선택 근거**(사용자): 커스텀 훅 기반 합성형 컴포넌트를 선호하고, React의 순수한
    API를 적극 활용하고자 한다. 앞으로도 컴포넌트 로직은 커스텀 훅으로 빼는 방식을
    **표준**으로 이어간다. 테스트 용이성 측면에서도 훅 방식을 선호한다.
- **Alternatives**:
  - 안 A(인라인): 변경 최소이나 로직이 컴포넌트+side effect에 묶여 단위 테스트·재사용이
    약하다.
  - 안 B(컴포넌트만 분리): UI는 독립 테스트 가능하나 저장·분기 로직이 NoteEditor에 남아
    커스텀 훅 패턴을 도입하지 못한다.
- **Consequences**:
  - 관심사 분리가 가장 명확하다. 순수 함수는 React 없이, `useTags`는 `renderHook`+mock
    context로, UI는 props/콜백으로 각각 단위 테스트할 수 있다.
  - 자동완성·필터 등 후속 확장 시 훅을 재사용하기 쉽다.
  - 파일 수와 인다이렉션이 늘고, 현재 코드베이스에 커스텀 훅·`lib/` 레이어 선례가 없어
    **새 컨벤션을 도입**한다 — 의도된 표준화이며, 정착 후 CLAUDE.md "컴포넌트 구현 패턴"에
    "컴포넌트 로직은 커스텀 훅으로 분리한다"를 추가 문서화한다.

## 4. 범위 밖 (Out of scope)

이번 작업에서 다루지 **않는** 항목. 필요 시 각각 별도 작업으로 분리한다.

- **검색·필터링**
  - 태그로 노트를 필터링하거나 검색하는 기능.
  - 다중 태그 AND/OR 조합 필터.
- **전역 태그 관리**
  - 전체 노트를 가로지르는 전역 태그 목록 화면.
  - 태그 입력 시 자동완성(기존 태그 제안).
  - 태그 이름 일괄 변경(rename) / 일괄 삭제.
  - 사용되지 않는 태그 정리(garbage collection).
- **목록(NoteList) 표시**
  - `NoteItem`에 태그 칩을 함께 노출하는 것.
  - 목록에서 태그 기반 정렬.
- **태그 부가 기능**
  - 태그 색상 지정 / 커스텀 색상.
  - 태그 정렬(알파벳순·사용빈도순 등) 옵션.
  - 태그 그룹/계층(중첩 태그, `parent/child`).
  - 태그별 노트 수 집계(badge count).
- **검증·제약 강화**
  - 태그 개수 상한 / 태그 길이 상한 같은 하드 제한.
  - 대소문자 정규화(`"React"`와 `"react"` 병합) — 현재는 정확 일치로 별개 태그.
  - 금칙어·특수문자 필터링.
- **데이터 정규화**
  - 별도 tags 컬렉션 / 참조 정규화(`tagId` 기반 모델).
  - 태그-노트 N:M 관계 테이블.
- **사용자 노출 에러 UI**
  - 토스트 등 사용자 알림 UI (현재 프로젝트 규약상 `console.error`만 사용).
- **권한·협업**
  - 태그 공유, 사용자별 태그 분리 등 멀티 유저 시나리오.

## 5. 용어 정의

| 용어             | 정의                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------- |
| 태그(tag)        | 노트를 분류·식별하기 위한 짧은 문자열. `Note.tags`에 `string[]`로 저장된다.                              |
| 칩(chip / badge) | 추가된 태그 하나를 시각적으로 표현하는 작은 UI 요소. hover 시 삭제(×) 버튼이 노출된다.                   |
| 확정 키          | 입력 중인 텍스트를 태그로 확정하는 키. **Enter** 또는 **쉼표(,)**.                                       |
| 편집 모드        | `selectedNoteId`가 존재하는 상태. 기존 노트를 수정하며, 태그 변경이 **즉시 저장**된다.                   |
| 생성 모드        | `isCreating`이 true인 상태. 노트 id가 아직 없어 태그는 로컬 state에만 쌓이고 최초 저장 시 함께 전송된다. |
| 즉시 저장        | 칩 추가/삭제 직후 `updateNote(id, { tags })`로 서버에 바로 반영하는 동작 (편집 모드 한정).               |
| 정확 일치        | 중복 판단 시 대소문자를 구분하는 비교 방식. `"React" !== "react"`.                                       |
| 단일 Context     | 모든 노트 서버 상태·CRUD 액션을 보유하는 `NotesContext`. 컴포넌트는 `useNotes()`로만 접근한다.           |
