# PRD: 노트 검색 (search)

> 단일 기준 문서. 이 기능에 대해 궁금하면 여기만 보면 된다.
> 기준 입력: [spec-fixed.md](./spec-fixed.md)

## 1. 개요

노트 앱에 검색 기능을 추가한다. 사용자가 사이드바의 검색 입력란에 키워드를 타이핑하면,
**제목과 본문**을 대상으로 **실시간 필터링**해 매칭되는 노트만 사이드바 목록에 남긴다.
노트는 이미 `NotesContext`에 전부 로드돼 있어 **서버 요청 없이 클라이언트에서** 필터링한다.

목적: 노트가 늘어났을 때 원하는 노트를 빠르게 찾는다.

## 2. 사용자 스토리

- **검색**: 사용자로서, 검색창에 키워드를 입력하면 제목·본문에 그 키워드가 포함된
  노트만 보고 싶다. 그래야 많은 노트 중 원하는 것을 빨리 찾는다.
- **결과 없음 인지**: 사용자로서, 매칭되는 노트가 없으면 "검색 결과가 없습니다"를 보고
  싶다. 그래야 빈 화면을 보고 당황하지 않는다.
- **초기화**: 사용자로서, 검색창을 비우면 즉시 전체 목록으로 돌아가고 싶다.
- **편집 연속성**: 사용자로서, 노트를 열어 보는 중에 검색해도 보던 노트가 사라지지 않길
  바란다.

## 3. 기술 결정 (ADR)

### ADR-1. 검색어 상태를 `App.tsx` 로컬 state로 둔다 (안 B)

**Context** — 검색 기능에는 "현재 검색어"라는 새 상태가 필요하다. 이 상태를 어디에 둘지가
설계의 핵심이다. 후보는 ① `NoteList` 내부 로컬, ② `App.tsx` 로컬(상태 끌어올림),
③ `NotesContext` 확장 세 가지였다. 노트 데이터는 이미 `NotesContext.notes`에 전부 로드돼
있어 서버 요청은 필요 없고, 순수하게 "어떤 노트를 보여줄지"를 거르는 UI 관심사다.

**Decision** — 검색어를 `App.tsx`의 `useState<string>`로 둔다(`selectedNoteId`·`isCreating`과
동급). 검색 입력(`SearchInput`)은 사이드바 상단에 두고, `query`를 `NoteList`에 prop으로
주입한다. 필터링(`title`/`content`에 대한 부분 문자열 매칭)은 `NoteList`가 `notes`를
받아 렌더 직전에 계산한다. `Note` 타입·`api/notes.ts`·`NotesContext`는 변경하지 않는다.

**Alternatives**

- **안 A (NoteList 자급자족)** — 거부 이유: 가장 적은 변경이지만 검색어 상태와 input이
  `NoteList`에 갇혀, "UI 전용 상태는 `App.tsx`에 모은다"는 기존 패턴과 어긋난다.
  검색 input을 헤더 등 다른 위치로 옮기기 어렵고, 선택 상태(`selectedNoteId`)와 검색
  상태가 서로 다른 층에 흩어진다.
- **안 C (Context 확장)** — 거부 이유: CLAUDE.md가 _"선택/생성 모드 같은 UI 전용 상태는
  Context에 절대 넣지 않는다"_ 고 명시한다. 검색어는 전형적인 UI 전용 상태이므로 Context에
  넣으면 서버 상태와 UI 상태의 분리 원칙을 정면으로 위반한다. 결합도도 올라가 테스트 시
  Context 모킹이 필요해진다.

**Consequences**

- (+) `selectedNoteId`와 같은 자리·같은 방식이라 기존 코드를 읽은 사람이 즉시 이해한다.
- (+) Context·API·타입 무변경 → 영향 범위가 좁고 회귀 위험이 낮다.
- (+) `NoteList`는 `query` prop만 받으면 되어 단위 테스트가 쉽다.
- (−) `query`를 `App.tsx → Layout/사이드바 → NoteList`로 prop drilling 해야 한다(한 단계라
  부담은 작다).
- (−) 필터링이 매 렌더마다 재계산된다. 강의 규모에선 무시 가능하나, 대량 데이터 시
  `useMemo`·debounce가 추후 필요할 수 있다(현재는 도입하지 않음).

### ADR-2. 매칭은 대소문자 무시 부분 문자열로 한다

**Context** — "매칭"의 의미를 코드 차원에서 고정해야 한다. 정규식·퍼지·형태소 분석 등
선택지가 있으나 강의용 노트 앱에는 과하다.

**Decision** — `query.trim()`을 소문자화한 뒤 `title`·`content`를 각각 소문자화해
`includes()`로 부분 문자열 포함을 판정한다. 둘 중 하나라도 포함하면 매칭. `trim()` 결과가
빈 문자열이면 필터를 적용하지 않고 전체를 보여준다.

**Alternatives**

- **정규식/퍼지 매칭** — 거부 이유: 구현·테스트 복잡도가 크고, 사용자가 정규식 특수문자를
  입력하면 예외 처리가 필요해진다. 강의 범위를 벗어난다.
- **대소문자 구분** — 거부 이유: 영문 노트에서 사용자가 대소문자를 정확히 맞춰야 해
  검색 실패가 잦아진다. 일반적 기대(대소문자 무시)와 어긋난다.

**Consequences**

- (+) 한 줄짜리 순수 함수로 떨어져 테스트가 단순하다.
- (+) 예측 가능하고 직관적이다.
- (−) 한글 초성 검색·유사어·오타 보정은 안 된다(의도된 제한, Out of Scope).

## 4. Out of Scope

이번 작업에서 **하지 않을 것**. 명시하지 않으면 범위가 새므로 항목을 콕 집는다.

- **매칭 텍스트 하이라이트** — `NoteItem`에서 매칭 글자를 `<mark>`로 강조하는 기능.
- **서버사이드 검색** — json-server `q`/`title_like`/`content_like` 파라미터 사용. 클라이언트
  필터링만 한다.
- **태그 기반 검색** — `tags` 필드 자체가 아직 없으므로 대상에서 제외.
- **퍼지/정규식/형태소 검색, 한글 초성 검색, 오타 보정.**
- **검색어 자동완성·추천·검색 기록(history).**
- **검색 결과 정렬·관련도 랭킹** — 기존 목록 순서를 그대로 유지.
- **debounce / `useMemo` 등 성능 최적화** — 현재 데이터 규모에선 불필요. 필요해지면 별도
  작업으로 도입.
- **검색 중 본문 내 매칭 위치로 스크롤/점프.**

## 5. 용어 정의 (Ubiquitous Language)

> spec-fixed.md의 용어 정의와 동기화한다.

| 용어              | 정의                                                                |
| ----------------- | ------------------------------------------------------------------- |
| 검색어(query)     | 사용자가 검색 입력란에 타이핑한 문자열.                             |
| 검색 대상(scope)  | 검색이 들여다보는 노트 필드 = `title` + `content`.                  |
| 매칭(match)       | 검색어가 노트의 제목 또는 본문에 부분 문자열로 포함되는 것.         |
| 필터링(filtering) | 매칭되는 노트만 사이드바 목록에 남기는 동작. 데이터 자체는 안 바뀜. |
| 결과 없음         | 노트는 존재하지만 검색어에 매칭되는 노트가 0개인 상태.              |
