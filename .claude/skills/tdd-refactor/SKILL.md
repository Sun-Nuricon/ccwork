# TDD Refactor

GREEN 단계(`tdd-green`)로 전부 초록이 된 코드의 **구조를 개선**하는 스킬. TDD의
REFACTOR 단계다. 핵심 원칙은 단 하나: **동작(테스트 통과)을 바꾸지 않고 구조만
바꾼다.** 테스트가 안전망이므로, 매 변경마다 테스트로 동작이 유지됨을 증명한다.

입력은 이슈 번호 하나(`$ARGUMENTS`)다. 그 번호로 이번 이슈에서 바뀐 `src/` 파일을
추려 리팩토링 후보를 찾고, **승인을 받은 뒤** 작은 단위로 안전하게 정리한다.

> **이 스킬의 본질**: 리팩토링은 "더 나은 코드"가 아니라 "동작은 같고 읽기·고치기
> 쉬운 코드"를 만드는 일이다. 빨간 테스트를 내거나 새 기능을 끼워 넣으면 그건
> 리팩토링이 아니다. 의심스러우면 더 작게 쪼개고, 매번 테스트로 확인한다.

## 입력

- `$ARGUMENTS` = **이슈 번호** 하나 (예: `/tdd-refactor 1` → `1`).
- 번호가 비어 있거나 숫자가 아니면 진행하지 말고 이슈 번호를 요청한다.
- 이슈 번호는 어떤 변경 범위를 다룰지(아래 3단계 `git diff`)와 맥락(`issue-{N}.md`)을
  잡는 데 쓴다.

## 절대 제약 (어기면 REFACTOR가 아니다)

리팩토링의 정의가 곧 제약이다. 아래를 어기면 그건 다른 작업(기능 추가·재설계)이다.

1. **새 기능 추가 금지.** 테스트가 요구하지 않는 동작·prop·분기·옵션을 추가하지
   않는다. 리팩토링은 기존 동작을 보존한다 — 늘리지 않는다.
2. **테스트 파일 수정 금지.** `*.test.ts` / `*.test.tsx`는 안전망이자 명세다.
   리팩토링이 테스트를 바꿔야만 통과한다면, 그건 동작을 바꾼 것 → 멈추고 보고한다.
3. **`src/` 밖 수정 금지.** 설정·문서·CI 등은 이 스킬의 범위가 아니다.
4. **대상 범위(git diff 결과) 밖 수정 금지.** 이번 이슈에서 바뀐 파일만 손댄다.
   "겸사겸사" 다른 파일을 정리하지 않는다 — 범위가 흐려지면 회귀 추적이 어려워진다.
5. **전부 초록인 상태에서만 시작.** 빨간 테스트가 있으면 리팩토링이 아니라 구현이
   안 끝난 것 → `tdd-green`으로 돌려보낸다.

## Workflow

순서대로 진행한다. **4단계의 승인 게이트**와 **5단계의 한 건씩 루프**가 안전의 핵심이다.

### 1. 프로젝트 컨벤션 파악

`CLAUDE.md`를 읽어 이 프로젝트의 **네이밍·아키텍처·상태 관리·API·에러 처리·스타일링**
규약을 파악한다. 리팩토링의 방향은 "내 취향"이 아니라 **이 코드베이스의 일관성**이다.
예: CRUD 동사 통일(`fetch/create/update/delete`), named export, `alert()` 금지·
`console.error`, 단방향 데이터 흐름(`useNotes()` 경유) 등. 스타일/className을 건드릴
일이 있으면 `design-system` 스킬도 거친다.

### 2. 시작 전 전체 통과 확인

```bash
npm test
```

- **전부 통과**해야 시작한다. 이게 리팩토링의 출발 안전망이다.
- 하나라도 실패하면 멈춘다 — 리팩토링이 아니라 GREEN이 안 끝난 상태다.
  `tdd-green {N}`으로 돌려보낸다.

### 3. 리팩토링 대상 파일 식별

이번 이슈에서 **실제로 바뀐 `src/` 파일**만 후보로 삼는다. 변경은 세 곳에 흩어져
있을 수 있으니 **셋 다** 모은다 — 하나만 보면 빠진다.

```bash
git diff main...HEAD --name-only -- src/          # ① 이미 커밋된 변경
git diff --name-only -- src/                       # ② 아직 커밋 안 한 수정(작업 트리)
git ls-files --others --exclude-standard -- src/   # ③ 새로 만든 파일(untracked)
```

- 세 결과를 합친 뒤 중복을 제거해 최종 대상 목록을 만든다.
- 결과에서 **테스트 파일(`*.test.ts` / `*.test.tsx`)을 제외**한다.
- 남은 파일 각각을 아래 **점검 기준**으로 검토한다. 기준에 걸리는 게 없으면 "정리할
  것 없음"도 정직한 결론이다 — 억지로 바꾸지 않는다.

> **왜 셋 다 보나**: `main...HEAD`(3-dot)는 _커밋된_ 변경만 보여준다. GREEN 직후
> 아직 커밋 전이면 ①은 비어 있고, 새로 만든 컴포넌트는 ③에만 잡힌다. 커밋 습관과
> 무관하게 대상을 놓치지 않으려면 ①②③을 합친다. 브랜치가 없거나 main 기준이
> 다르면 base를 상황에 맞게 조정한다.

#### 점검 기준 (스킬 내장)

- **중복 제거** — 같은 로직/구조가 두 군데 이상 반복되는가? (단, 우연히 닮은 코드를
  무리하게 합치지 않는다. 같은 _이유로_ 바뀔 것만 합친다.)
- **네이밍 명확성** — 변수·함수·컴포넌트 이름이 의도를 드러내는가? `data`, `tmp`,
  `handleClick2` 같은 모호한 이름이 있는가? 프로젝트 네이밍 규약과 맞는가?
- **단일 책임** — 하나의 함수/컴포넌트가 너무 많은 일을 하는가? 렌더와 계산, 페치와
  변환이 한 덩어리로 엉켜 있는가?
- **불필요한 복잡도** — 매직 넘버/문자열, 과도한 중첩(깊은 if/삼항), 쓰지도 않는
  추상화·일반화, 죽은 코드.
- **CLAUDE.md 컨벤션 불일치** — 프로젝트의 확립된 패턴(위 1단계)과 어긋나는 코드.

### 4. 대상 목록 보고 → 승인 대기 〈게이트〉

찾은 후보를 **개발자에게 보고하고 멈춘다.** 승인 없이 코드를 바꾸지 않는다. 이
게이트가 있는 이유: 리팩토링은 주관이 섞이고, 개발자가 "지금은 건드리지 말자"고 할
권리가 있기 때문이다.

보고 형식(후보별 한 줄):

```
- [파일:라인] 기준 — 무엇을, 왜, 어떻게 (예상 변경)
  예) src/components/TagList.tsx:9  [복잡도] index 기반 key가 중복 태그에서 취약 →
      안정 key 전략으로 교체 제안
```

- 우선순위(영향 큰 것 먼저)나 위험도를 함께 적으면 좋다.
- 개발자가 일부만 승인할 수 있다. 승인된 항목만 5단계로 가져간다.
- 후보가 없으면 "정리할 것 없음"을 보고하고 종료한다(7단계로).

### 5. 한 건씩: 변경 → 테스트 → 통과 확인

승인된 항목을 **하나씩** 처리한다. 한 번에 하나가 원칙이다 — 여러 개를 몰아 바꾸면
어느 변경이 회귀를 냈는지 못 짚는다.

1. 후보 하나를 리팩토링한다(동작 불변, 구조만).
2. `npm test`로 **전체** 통과를 확인한다(해당 파일만이 아니라 회귀 포함 전체).
3. 통과하면 다음 후보로. 커밋 단위로 끊고 싶으면 여기서 끊는다(커밋은 선택).

### 6. 테스트가 깨지면 즉시 롤백

리팩토링 중 테스트가 빨개지면, 그 변경은 **동작을 바꾼 것**이다. 디버깅으로 끌고
가지 말고 **즉시 직전 상태로 되돌린다**(해당 변경만 revert/되돌리기). 안전망이 빨간
채로 다음 변경을 쌓지 않는다.

- 되돌린 뒤, 같은 목표를 **다른 접근**으로 다시 시도한다(더 작게 쪼개거나, 중간 단계를
  두거나). 두세 번 시도해도 동작 보존이 안 되면, 그 항목은 "리팩토링만으로는 불가"로
  보고하고 넘어간다(설계 변경이 필요한 신호 — 별도 작업).

### 7. 리팩토링 전후 요약

마무리로 정리해 보고한다:

- 처리한 항목별 **전/후 변경 요약**(무엇을 왜 바꿨고, 어떤 기준에 해당했는지).
- 전체 테스트 결과(여전히 모두 초록).
- 승인됐지만 롤백/보류한 항목과 이유.
- 손대지 않기로 한 후보(있다면)와 근거.
- 다음 단계 안내(커밋 등).

## "좋은 리팩토링"이란 무엇인가 (REFACTOR의 핵심)

- **좋은 REFACTOR** ✅
  - 두 컴포넌트에 복붙된 동일 칩 렌더 로직을 한 곳으로 추출 → 테스트 그대로 통과.
  - `const M = 3` 매직 넘버에 의미 있는 이름 부여 → 동작 동일.
  - 깊은 삼항 중첩을 early return으로 평탄화 → 출력 동일.
  - 프로젝트 규약(`add`→`create`)에 맞게 함수명 통일 → 호출부도 같이 갱신, 동작 동일.
- **나쁜 REFACTOR** ❌ (하지 않는다)
  - "이참에" 새 prop/기능 추가 — 그건 기능 작업.
  - 테스트를 고쳐서 통과시키기 — 동작을 바꾼 것.
  - diff 범위 밖 파일까지 정리 — 범위 이탈.
  - 안 쓰는 일반화·추상 레이어 도입("나중에 필요할지도") — 복잡도만 늘린다.

판단이 서지 않으면 물어본다: "이 변경 후 테스트를 하나도 안 고쳤는데 전부 통과하는가?"
그렇다면 리팩토링이다. 아니라면 멈춘다.

## 하지 않는 것 (범위 밖)

- **기능 추가/동작 변경** — REFACTOR의 정의에 반한다.
- **테스트 수정·추가·삭제** — 안전망은 고정. 부족하면 RED/`test-scenarios`로.
- **`src/`·diff 범위 밖 수정** — 범위를 좁게 유지해야 회귀를 추적할 수 있다.
- **승인 없는 변경** — 4단계 게이트를 건너뛰지 않는다.
- **여러 이슈 동시 처리** — 한 번에 이슈 1개.
- **커밋 강제** — 커밋은 개발자 판단(원하면 변경 단위로 끊어주는 정도).

## 도구 메모

- 변경 파일: 커밋된 것 `git diff main...HEAD --name-only -- src/` + 미커밋 `git diff --name-only -- src/` + 신규 `git ls-files --others --exclude-standard -- src/`를 합쳐서 본다(테스트 파일 제외).
- 전체 테스트: `npm test`(= `vitest run`). 매 변경 후 **전체**를 돌려 회귀를 잡는다.
- 되돌리기: 커밋 전이면 해당 변경만 수동 복원, 커밋 후면 그 변경만 revert.
- 맥락 소스: `CLAUDE.md`(컨벤션) + `docs/features/tag/issue-{N}.md`(이슈 의도).
