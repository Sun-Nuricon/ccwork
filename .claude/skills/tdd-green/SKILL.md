# TDD Green

RED 단계(`tdd-red`)가 만든 **실패하는 테스트**를 통과시키는 **최소 구현**만 담당하는
스킬. TDD의 GREEN 단계다. 테스트 설계(RED)·구조 개선(REFACTOR)은 범위 밖이다.

입력은 이슈 번호 하나(`$ARGUMENTS`)다. 그 번호의 테스트들을 "초록불"로 만드는 것이
유일한 목표이며, **테스트가 요구하는 동작만큼만** 구현한다.

> **이 스킬의 본질**: 테스트가 명세다. 테스트를 통과시키는 가장 단순한 코드를 쓰고
> 멈춘다. "나중에 필요할 것 같아서" 미리 만드는 추상화·옵션·필드는 GREEN을 오염시킨다.
> 테스트가 빨갛다 → 코드를 더한다 → 초록이 된다 → 멈춘다. 이 루프가 전부다.

## 입력

- `$ARGUMENTS` = **이슈 번호** 하나 (예: `/tdd-green 1` → `1`).
- 번호가 비어 있거나 숫자가 아니면 진행하지 말고 이슈 번호를 요청한다.
- `docs/features/tag/issue-{N}.md`(시그니처·시나리오·AC)와 그 이슈의 테스트 파일이
  이미 있어야 한다. 테스트가 없으면 진행하지 말고 먼저 `/tdd-red {N}`로 RED를
  끝내야 한다고 안내한다.

## 절대 제약 (어기면 GREEN이 깨진다)

1. **테스트 파일은 절대 수정·삭제하지 않는다.** `*.test.ts` / `*.test.tsx`는 명세다.
   테스트가 틀렸다고 판단되면 고치지 말고 멈춰서 보고한다(RED로 돌아갈 일이다).
2. **테스트에 없는 기능은 구현하지 않는다.** 테스트가 단언하지 않는 prop·필드·분기·
   상태는 만들지 않는다. "있으면 좋을" 것은 GREEN의 적이다.
3. **불필요한 추상화 금지.** 테스트 하나를 통과시키는데 제네릭·팩토리·설정 객체·추상
   레이어가 필요 없다면 만들지 않는다. 가장 직접적인 코드를 쓴다.
4. **디자인은 적용하되 임의 추가 금지.** 디자인 문서(아래 3단계)에 명시된 스타일은
   그대로 반영하되, 문서에 없는 시각 요소(아이콘, 애니메이션, 색)를 지어내지 않는다.
5. **프로젝트 규약을 따른다.** `CLAUDE.md`의 아키텍처/네이밍/에러 처리/API 패턴을
   그대로 따른다(예: `alert()` 금지·`console.error`, CRUD 동사 통일, named export 등).

## Workflow

순서대로 진행한다. 핵심은 **4~7의 한 건씩 통과시키는 루프**다.

### 1. 실패 목록 확인

```bash
npm test
```

- 출력의 `Test Files` / `Tests` 수와 **어떤 테스트가 왜 실패하는지**를 본다.
- 실패 유형을 구분한다:
  - **collection error**(`Failed to resolve import "./TagList"` 등) → 대상 모듈이
    아예 없어 그 파일의 테스트가 **실행조차 안 됨**. → 2단계로.
  - **assertion 실패** → 모듈은 있고 동작이 없거나 틀림. → 정상적인 GREEN 출발점.

### 2. collect 실패 감지 → stub 생성

RED 단계는 `src/`를 건드리지 않으므로, import 대상 모듈이 없어 테스트가 **collect
단계에서 통째로 실패**하는 게 보통이다. 이러면 vitest가 보고하는 `Tests` 수가 실제
시나리오 수보다 적게 잡혀, 무엇을 통과시켜야 하는지 전체 그림이 안 보인다.

**감지**: `docs/features/tag/issue-{N}.md`의 **시나리오 항목 총 건수**와 vitest가
보고하는 `Tests` 수를 비교한다. 시나리오 항목은 `- [정상] …` / `- [경계] …` /
`- [예외] …` 형식의 줄(완료 표시된 `- [x] …` 줄 포함)이다. `- (해당 없음)`처럼
카테고리 태그가 없는 줄은 시나리오가 아니므로 세지 않는다. **불일치 = 인식 안 된
테스트가 있다**는 뜻.

**해결**: 누락된 import 대상마다 **시그니처만 있는 stub 파일**을 만들어 전체 테스트가
collect되게 한다. stub은 "비어 있지만 import는 되는" 최소 형태다.

```tsx
// src/components/TagList.tsx — stub (시그니처만, 동작 없음)
interface TagListProps {
  tags: string[];
}

export function TagList({ tags }: TagListProps) {
  return null; // GREEN 루프에서 채운다
}
```

```ts
// src/lib/tags.ts — 함수 stub
export function parseTags(input: string): string[] {
  return []; // GREEN 루프에서 채운다
}
```

- stub의 시그니처(이름·props·인자·반환 타입)는 `issue-{N}.md`의 **확정 시그니처**를
  그대로 따른다. 임의로 늘리지 않는다.
- 타입(`Note.tags` 등)이 없어 collect가 깨지면 해당 타입 필드도 시그니처대로 추가한다.
- stub을 만든 뒤 `npm test`를 다시 돌려 **모든 테스트가 인식되고(=Tests 수 일치),
  이제 assertion으로 실패**하는지 확인한다. 여기서부터가 진짜 GREEN 출발선이다.

### 3. 디자인 컨텍스트 로드

UI 컴포넌트를 구현한다면, 동작뿐 아니라 **시각 스펙**도 함께 맞춰야 다음 단계에서
다시 손대지 않는다. 다음 순서로 컨텍스트를 모은다.

1. **디자인 시스템** — 이 프로젝트의 디자인 규칙은 `docs/design-system/`에 있고
   `design-system` 스킬이 작업에 필요한 문서만 골라 로드한다(토큰 단일 원천은
   `docs/design-system/tokens.css`). **className/스타일을 쓰는 작업이면 먼저
   `design-system` 스킬을 거친다**(CLAUDE.md 규약). 구현 대상 컴포넌트의 색상·간격·
   레이아웃·radius·상태별(hover/선택/비활성) 표현을 파악한다.
   - 디자인 시스템 문서를 못 찾으면, 비슷한 기존 컴포넌트(`NoteItem`, `NoteEditor`)의
     실제 클래스를 참고해 톤을 맞춘다.
2. **이슈별 디자인 참고** — `docs/features/tag/issue-{N}.md`에 "디자인 참고" 섹션이
   있으면 함께 확인한다(해당 화면에 한정된 추가 지침).
3. **코드 컨벤션** — `CLAUDE.md`의 스타일링 섹션(Tailwind v4 `@theme` 토큰, `bg-card`·
   `text-muted-foreground` 등 명명 규약)을 참조한다.

디자인 문서가 전혀 없으면 이 단계를 건너뛰고 `CLAUDE.md` 컨벤션만 따른다. 순수 로직
함수처럼 시각 요소가 없는 대상도 이 단계는 건너뛴다.

### 4. 첫 실패 테스트를 통과시키는 최소 코드 작성

실패 목록의 **맨 위 테스트 하나**를 고른다. 그 테스트가 단언하는 동작만 충족하도록
구현한다.

- 테스트가 보는 것(텍스트·역할·반환값·호출)만 만든다. 그 이상은 만들지 않는다.
- UI라면 동작을 충족하되 **3단계에서 파악한 스타일 스펙을 함께 적용**한다.
  `design-system`/디자인 참고에 명시된 Tailwind 클래스·레이아웃 구조·상태별 표현을
  그대로 쓴다. 문서에 없는 시각 요소는 더하지 않는다.
- 새 엔드포인트·Context 액션이 필요하면 `CLAUDE.md`의 3단계(`api/notes.ts` 함수 →
  `NotesContext` 액션 → 컴포넌트는 `useNotes()`로 접근)를 그대로 따른다.

### 5. 실행 → 통과 확인 + 회귀 점검 〈피드백 루프〉

```bash
npx vitest run <대상 테스트 파일> -t "<it 이름>"   # 빠른 단건 확인
npm test                                          # 회귀 포함 전체 확인
```

- 대상 테스트가 **통과**하고, 기존에 통과하던 테스트가 **여전히 통과**(회귀 없음)하면
  6단계로.
- 대상 테스트가 **아직 실패**하면: 에러 메시지를 읽고 원인을 분석해 코드를 수정한 뒤
  5단계를 다시 실행한다. **최대 5회 반복**.
- **5회 후에도 실패하면 중단**하고, 실패 원인(에러 메시지 + 분석 + 막힌 지점)을
  개발자에게 보고한다. 테스트를 고쳐서 억지로 통과시키지 않는다.
- 한 테스트를 통과시키며 **다른 테스트가 깨졌다면**(회귀) 그것도 이 루프 안에서 함께
  해결한다.

### 6. 시나리오 항목 완료 표시

방금 통과시킨 시나리오에 해당하는 `docs/features/tag/issue-{N}.md`의 줄 맨 앞에
`[x]` 마커를 붙여 완료 표시한다. **카테고리 태그는 보존**한다:

```
- [정상] TagList — should render a chip ...      →   - [x] [정상] TagList — should render a chip ...
```

이렇게 하면 카테고리(`[정상]`)는 그대로 남고, 완료 여부만 `[x]` 접두로 추적된다.
남은 시나리오 = `- [정상]/[경계]/[예외]`로 시작하는(아직 `[x]` 안 붙은) 줄. 진행
상황을 문서가 추적하게 한다.

### 7. 다음 실패 테스트로 → 4단계 반복

남은 실패 테스트가 없을 때까지 4~6을 반복한다. 매번 "하나 통과 → 전체 초록 유지"를
지킨다. 전부 통과하면 8단계로.

### 8. 커버리지 측정 (참고용)

전체가 통과한 뒤에만 측정한다.

```bash
npx vitest run --coverage
```

- 미커버 라인(Uncovered Line #s)을 확인한다.
- 미커버가 있으면 **시나리오에서 빠진 케이스인지** 판단해 개발자에게 보고한다(예:
  "에러 분기 X가 어떤 테스트로도 실행되지 않음 — 시나리오 누락 가능성").
- **커버리지를 올리려고 테스트를 추가하지 않는다.** 새 테스트는 RED/`test-scenarios`의
  몫이다. 커버리지는 누락 발견용 신호로만 쓴다.

### 9. 결과 요약

한 번에 정리해 보고한다:

- 통과시킨 테스트 수(= 체크한 시나리오 수)와 전체 결과(모두 초록 확인).
- 새로 만들거나 수정한 `src/` 파일 목록(stub 포함).
- 커버한 AC(`issue-{N}.md`의 AC 커버리지 표 기준).
- 커버리지 측정에서 드러난 미커버/시나리오 누락 의심 지점.
- 막혀서 중단했다면 그 테스트와 원인.
- 다음 단계 안내: 필요하면 **REFACTOR**(동작 유지한 채 정리) 또는 커밋.

## "최소 구현"이란 무엇인가 (GREEN의 핵심)

테스트를 통과시키는 데 **꼭 필요한 코드만** 쓴다. 판단 기준:

- **좋은 GREEN** ✅
  - 테스트가 `['react','study']` 두 칩을 기대 → `tags.map`으로 칩을 렌더.
  - 빈 배열에서 칩이 없어야 함 → 같은 `map`이 자연히 처리(추가 분기 불필요).
  - 디자인 문서가 칩 스타일을 정의 → 그 클래스를 그대로 입힘.
- **나쁜 GREEN** ❌ (하지 않는다)
  - 테스트에 없는 `onTagClick`·`maxTags`·`variant` prop을 "쓸 것 같아서" 추가.
  - 정렬·중복 제거 등 테스트가 요구하지 않은 로직을 미리 넣음.
  - 문서에 없는 색/아이콘/애니메이션을 임의로 추가.
  - 한 컴포넌트면 될 것을 추상 베이스 + 구현체로 쪼갬.

막히면 "이 줄을 지워도 빨간 테스트가 그대로인가?"를 물어본다. 그렇다면 그 줄은
지금 필요 없다.

## 하지 않는 것 (범위 밖)

- **테스트 수정/추가/삭제** — 어떤 이유로도. 테스트가 틀린 것 같으면 멈추고 보고한다.
- **리팩터(REFACTOR)** — 중복 제거·구조 개선은 전부 초록이 된 다음, 별도 단계.
- **테스트에 없는 기능 구현** — 명세에 없는 동작은 GREEN의 범위가 아니다.
- **커버리지용 테스트 작성** — 누락은 보고만 한다.
- **커밋** — 이 스킬은 초록불 + 체크박스 갱신에서 끝난다(커밋은 별도).
- **여러 이슈 동시 처리** — 한 번에 이슈 1개.

## 도구 메모

- 단건: `npx vitest run <파일> -t "<it 이름>"`. 전체: `npm test`(= `vitest run`).
- 커버리지: `npx vitest run --coverage`(또는 `npm run test:coverage`). 리포트는
  `coverage/index.html`. `reportOnFailure: true`라 실패가 남아도 리포트는 나오지만,
  커버리지는 **전부 통과한 뒤** 보는 게 의미 있다.
- Vitest 3 `globals: true`라 테스트는 import 없이 동작한다(구현 코드에는 무관).
- 명세 소스는 `docs/features/tag/issue-{N}.md` + 그 이슈의 테스트 파일. 이슈 본문
  `issues.md`나 GitHub를 다시 읽지 않는다 — 이미 확정된 산출물이다.
