# TDD Loop

GitHub 이슈 **하나**를 받아, CLAUDE.md의 "TDD 이슈 사이클" 7단계를 **순서대로** 끝까지
진행하는 **컨테이너**다. 각 단계의 실제 작업은 이미 만들어진 스킬/에이전트가 하고,
이 컨테이너는 딱 세 가지만 책임진다.

1. **사전 점검** — 안전하게 시작할 수 있는 상태인지(이슈 존재·클린 트리·올바른 브랜치) 확인하고 작업 브랜치를 만든다.
2. **순서 보장** — 정해진 7단계를 정해진 순서로 하나씩 호출한다.
3. **실패 시 정지** — 어느 단계에서 왜 멈췄는지 분명히 알리고 그 자리에서 중단한다.

> **이 스킬의 본질은 "얇은 오케스트레이터"다.** 각 단계의 판단·구현·검증은 그 단계
> 스킬이 하고, 그 안의 **사용자 승인 게이트도 그대로 살아 있다**. 컨테이너는 게이트를
> 대신 통과시키거나 새로 만들지 않는다 — 순서만 엮는다. 그래서 "자동화"라기보다
> "정해진 길로 안내하며 매 갈림길에서 사람이 결정하게 두는" 장치에 가깝다.

## 입력

- `$ARGUMENTS` = **GitHub 이슈 번호** 하나 (예: `/tdd-loop 3` → `3`).
- 번호가 비었거나 숫자가 아니면 진행하지 말고 이슈 번호를 요청한다.
- 이 번호를 전 과정에서 `{N}`으로 쓴다(하위 스킬 인자·브랜치명·PR 본문 `Closes #{N}`).

## 핵심 원칙 (컨테이너의 규칙)

이 규칙들이 깨지면 컨테이너의 의미가 사라진다.

1. **각 단계는 그 스킬을 "그대로" 호출한다.** 로직을 여기서 재구현하지 않는다.
   `/test-scenarios {N}` → `/tdd-red {N}` → `/tdd-green {N}` → `@ac-verifier {N}` →
   `/tdd-refactor {N}` → `/security-review {N}` → `/create-pr <base>` 순서 그대로.
2. **하위 스킬의 승인 게이트는 유지한다.** 예: `test-scenarios`의 시그니처·시나리오 2게이트,
   `tdd-refactor`·`security-review`·`create-pr`의 승인 게이트는 **사용자가 응답해야**
   다음으로 넘어간다. 컨테이너가 대신 "승인"하지 않는다.
3. **컨테이너는 추가 게이트를 만들지 않는다.** 단계와 단계 사이에 "다음 단계 진행할까요?"
   같은 질문을 새로 끼워넣지 않는다. 한 단계가 끝나면 **한 줄 진행 메시지**만 찍고 곧바로
   다음 단계를 호출한다. (멈춤은 오직 하위 스킬 내부 게이트에서만 일어난다.)
4. **단계가 실패하면 그 자리에서 중단한다.** 어느 단계에서, 어떤 이유로 멈췄는지와
   **재개 방법**(그 단계 스킬을 단독으로 다시 호출)을 알리고 종료한다. 다음 단계로 넘어가
   실패를 덮지 않는다.

## Workflow

### 0. 사전 점검 (Preflight) — 하나라도 실패하면 중단

여기서 통과하지 못하면 **1단계로 가지 않는다**. 각 실패는 이유와 함께 사용자에게 알린다.

1. **이슈 확인** — `gh issue view {N}`로 본문과 완료조건(AC)을 읽는다.
   - `gh`가 없거나 인증 안 됨/이슈 없음이면: 이 프로젝트의 이슈 단일 소스인
     `docs/features/tag/issues.md`의 `## 이슈 {N} — ...` 섹션으로 폴백해 AC를 읽는다
     (test-scenarios와 동일 규약). 이마저 없으면 어떤 이슈가 있는지 알리고 중단.
2. **클린 트리 확인** — `git status --porcelain`.
   - 커밋되지 않은 변경이 남아 있으면 **중단**한다(안전 차원 — 브랜치를 바꾸면 유실·혼선
     위험). 무엇이 남아 있는지 보여주고, 커밋/스태시 후 다시 `/tdd-loop {N}`을 권한다.
3. **현재 브랜치 확인** — `git rev-parse --abbrev-ref HEAD`가 `feature/<spec>` 꼴인지 본다.
   - 이 값을 **`SPEC_BRANCH`(= PR base)** 로 기억한다. `<spec>` = `feature/` 뒤 부분.
   - `feature/…`가 아니면(예: `main`) 중단하고, spec 브랜치에서 시작하라고 안내한다.
     선행 이슈가 있으면 그 이슈가 머지된 feature 브랜치에서 시작해야 한다(CLAUDE.md 규약).
4. **작업 브랜치 결정** — 이슈 슬러그로 `feat/issue-{N}-<slug>`를 만든다
   (`<slug>` = 이슈 제목을 kebab-case로; 제목을 못 읽으면 `feat/issue-{N}`).
   - `git branch --list "feat/issue-{N}*"`로 **이미 있는지** 확인.
   - **있으면 = 동일 이슈 재실행**으로 보고 **사용자에게 확인**한다(이 확인은 안전을 위한
     것으로, 3번 원칙의 "추가 게이트" 예외다): 기존 브랜치를 **덮어쓸지**(체크아웃해 이어서)
     / **취소할지**. 사용자가 답하기 전엔 진행하지 않는다.
   - **없으면** `SPEC_BRANCH`에서 분기하고 체크아웃한다:
     `git switch -c feat/issue-{N}-<slug> <SPEC_BRANCH>`.
5. 위 중 **하나라도 실패**하면(명령 에러·조건 불충족) 이유를 밝히고 **중단**한다.

통과하면 진행 메시지 한 줄만 찍고(예: `사전 점검 통과 · feat/issue-{N}-<slug> 준비 완료 · 1단계 시작`)
곧바로 1단계로 간다.

### 1. 시그니처 + 시나리오 — `/test-scenarios {N}`

`test-scenarios` 스킬을 호출한다. 이 스킬 **내부에** 승인 게이트가 둘 있다(시그니처,
시나리오). 두 게이트는 그대로 작동하므로 **사용자가 각각 승인해야** 다음으로 간다.
컨테이너는 여기 개입하지 않는다. 완료되면 진행 메시지 한 줄 → 2단계.

### 2. 실패 테스트 작성 (RED) — `/tdd-red {N}`

`tdd-red` 스킬을 호출한다. 승인된 시나리오를 실패하는 테스트로 옮긴다. import 대상 모듈이
없어 **collect가 실패**하면 그 스킬의 규약대로 시그니처만 있는 stub 생성 안내가 나온다.
전부 "의도대로 실패"함을 확인하면 진행 메시지 → 3단계.

### 3. 최소 구현 (GREEN) — `/tdd-green {N}`

`tdd-green` 스킬을 호출한다. 실패 테스트를 통과시키는 **최소 구현**만 하고, 회귀를
감시하며 최대 5회 피드백 루프를 돈다. **전부 초록**이 되면 진행 메시지 → 4단계.
(초록이 되지 못하고 막히면 4번 원칙대로 여기서 중단한다.)

### 4. AC 충족 독립 검증 — `@ac-verifier {N}`

`ac-verifier` 에이전트를 호출한다. **"테스트 통과 ≠ AC 충족"** 이므로, GREEN이 초록이어도
AC 의도가 실제로 충족됐는지 독립 검증한다. **이 단계는 생략하지 않는다.**

- **갭 없음** → 진행 메시지 → 5단계.
- **갭 있음** → 컨테이너는 **사용자에게 갭을 보고**하고 판단을 맡긴다. 시나리오 보강으로
  닫으려면 **1단계(`/test-scenarios {N}`)로 되돌아가** RED→GREEN을 다시 태우고 재검증한다.
  이 되돌림은 사용자 지시로 한다 — 컨테이너가 임의로 루프를 반복하지 않는다.

### 5. 구조 개선 (REFACTOR) — `/tdd-refactor {N}`

`tdd-refactor` 스킬을 호출한다. **전부 초록인 상태에서만** 시작한다. 리팩토링 대상 보고 후
승인 게이트가 있고, 변경마다 `npm test`로 초록을 확인하며 깨지면 즉시 롤백한다. 완료되면
진행 메시지 → 6단계.

### 6. 타입·보안 점검 — `/security-review {N}`

`security-review` 스킬을 호출한다(커밋 직전 게이트). `tsc --noEmit`·`npm audit`·환경변수
노출을 수집해 셋(즉시 수정/권장/무시 가능)으로 분류 보고하고, **승인 후 "즉시 수정 필요"
항목만** 고친 뒤 재스캔으로 클린을 확인한다. 완료되면 진행 메시지 → 7단계.

### 7. 통합·PR — `/create-pr <SPEC_BRANCH>`

`create-pr` 스킬을 호출하되 **base로 0단계에서 기억한 `SPEC_BRANCH`를 넘긴다**
(예: `/create-pr feature/tag-spec`). 이 스킬은 초안 승인 게이트 → `npm run test:e2e`
게이트 → 통과 시 push + PR 생성을 한다. 컨테이너는 PR이 이슈를 닫도록 다음을 챙긴다.

- **커밋 메시지가 commitlint를 통과**하는지(제목 `type: subject`, 빈 줄, 본문 2줄 이상).
- **PR base = `SPEC_BRANCH`** (이슈 브랜치 → spec 브랜치 규약).
- **PR 본문에 `Closes #{N}` 포함** — 머지 시 이슈가 자동으로 닫히도록.
- 생성 성공 후 **이슈에 PR 링크 코멘트**: `gh issue comment {N} --body "PR: <URL>"`
  (`gh` 없으면 compare URL을 출력해 수동 코멘트를 안내).

PR URL을 보고하면 사이클 완료다. (E2E 실패 시 create-pr가 PR을 만들지 않고 근본 원인 분석을
안내한다 — 그 경우 4번 원칙대로 여기서 멈추고, 고친 뒤 다시 `/create-pr <SPEC_BRANCH>`.)

## 진행 메시지 형식

단계 사이에는 **질문이 아닌 상태 한 줄**만 찍는다. 예:

```
✓ 2/7 RED 완료 (실패 테스트 5건, 의도대로 실패) → 3단계 GREEN 시작
```

실패로 중단할 때는 **어디서·왜·어떻게 재개**를 함께 준다:

```
✗ 3/7 GREEN 중단 — 5회 루프 내 초록 실패(테스트 2건 여전히 red).
  재개: 원인 파악 후 /tdd-green {N} 단독 재실행. 나머지 단계는 진행하지 않음.
```

## 하지 않는 것 (범위 밖)

- **단계 로직 재구현** — 시나리오·테스트·구현·검증·리뷰·PR은 각 하위 스킬의 몫. 컨테이너는
  호출·순서·정지만 한다.
- **하위 스킬 게이트 대리 통과** — 승인이 필요한 지점을 사용자를 대신해 넘기지 않는다.
- **단계 사이 추가 게이트 생성** — "다음 진행할까요?"를 새로 끼우지 않는다(예외: 0단계
  재실행 확인, 4단계 AC 갭 보고 — 둘 다 안전·정확성 목적의 확인이다).
- **실패 덮고 전진** — 한 단계라도 실패하면 다음 단계로 넘어가지 않는다.
- **여러 이슈 동시 처리** — 한 번에 이슈 1개. 다른 이슈는 다시 `/tdd-loop`.
- **머지·이슈 클로즈 직접 수행** — PR 생성과 링크 코멘트까지가 범위. squash merge는 사람이
  GitHub에서(`Closes #{N}`로 머지 시 이슈는 자동 클로즈).

## 도구 메모

- 이슈/AC: `gh issue view {N}`(우선) → 없으면 `docs/features/tag/issues.md`의
  `## 이슈 {N}` 섹션으로 폴백.
- 트리/브랜치: `git status --porcelain`, `git rev-parse --abbrev-ref HEAD`,
  `git branch --list "feat/issue-{N}*"`, `git switch -c feat/issue-{N}-<slug> <SPEC_BRANCH>`.
- 하위 호출: `/test-scenarios {N}` · `/tdd-red {N}` · `/tdd-green {N}` · `@ac-verifier {N}` ·
  `/tdd-refactor {N}` · `/security-review {N}` · `/create-pr <SPEC_BRANCH>`.
- PR 링크 코멘트: `gh issue comment {N} --body "PR: <URL>"`(gh 없으면 compare URL 안내).
- 한글 인코딩: 커밋·PR 본문은 파일로 넘긴다(`git commit -F`, `gh pr create --body-file`) —
  실제 처리는 하위 스킬(create-pr)이 하지만 컨테이너도 이 규약을 깨지 않는다.
